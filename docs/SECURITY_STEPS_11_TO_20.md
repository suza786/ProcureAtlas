# Security and robustness: steps 11–20

This update implements the ten tasks supplied after the original steps 1–10.

1. Internal tenders, search, buyers, awards, competitors, markets and market-pulse routes use the existing tenant authentication policy. Anonymous reads are permitted only by explicit DEMO_MODE; deploy with DEMO_MODE=false. Tender detail alerts are scoped to the caller tenant.
2. Owner administration is transactional, requires an owner to manage another owner or grant ownership, and preserves at least one owner. Password resets and role changes revoke the user's sessions and API keys. User deletion revokes credentials in the same transaction and cannot delete owners.
3. Login validates emails and password types/lengths, including bcrypt's 72-byte limit. Account and IP token buckets bound attempts. Failed counters use atomic increments and successful session creation rechecks password/lock state in a transaction. Set TRUST_PROXY_HEADERS=true only behind a proxy that overwrites client-supplied forwarding headers; otherwise requests share the conservative unknown-IP bucket. New/reset passwords require 12 characters; existing shorter passwords can still sign in.
4. All handlers use shared JSON error handling for intentional responses, malformed JSON, Zod errors and common Prisma conflicts. Unexpected failures return a generic 500; Next framework control-flow exceptions remain intact.
5. Shared Zod schemas validate every JSON mutation, route IDs, relevant query filters, dates, currencies, finite amounts and pagination. JSON bodies are limited to 1 MiB; page sizes are 1–100 (embedding search: 50), offsets 0–100,000. Unsupported states and automatic approval steps are rejected.
6. TypeScript build checking is enabled. Proposal list and detail types differ explicitly, scoring uses its shared response type and query filters use Prisma types. Standalone websocket examples are excluded from application compilation because their optional socket dependencies are not installed; application code, scripts and tests remain checked.
7. The stale Bangla assertion now matches the existing translation; the fallback test deliberately creates an English-only key. Regression tests cover roles, API scopes, tenant boundaries, JSON errors, validation, login/approval concurrency and real SQLite owner protection.
8. Seeding requires SEED_DEMO_DATABASE_URL pointing to an absolute SQLite filename ending in demo.db and refuses NODE_ENV=production. Apply the Prisma schema to that dedicated demo database first. Run with Bun, or Node 22.18+ using `node --experimental-strip-types scripts/seed.ts`. One transaction refreshes only atlas-demo, removes its newer tenant records and upserts shared fixtures without overwriting existing shared data. No application database is seeded by default. A disposable-database integration test runs the full seed twice and preserves another tenant's data.
9. Mock connector runs return preview items with stable IDs and a mock source namespace. They never write the shared catalog or connector-run table; the authenticated HTTP action may still create an audit event. Production rejects mock runs and live ingestion refuses records marked as samples. Historical mock catalog rows require operator review; this update does not delete catalog data.
10. Approval decisions require the assigned user/email and role, a pending decision and approved earlier steps. A conditional update prevents double decisions. New proposals receive all active submission/pricing/legal chain steps, or a manager submission approval when no submission chain exists. Direct approval/submission status changes require completed workflow approvals. Pursuit creation cannot start at a submitted or already-decided stage.

Existing approval chains remain in place. If they contain nonconsecutive orders, unsupported roles or nonexistent assigned users, an administrator must correct them. Old workflows missing configured steps fail closed instead of submitting prematurely; start a new proposal under a valid chain rather than treating incomplete old workflows as approved. The schema is unchanged from the steps 1–10 upgrade, and this batch does not reset or seed the workspace database.
