# Portable deployment

Use Node.js 22.13 or newer; Node.js 24 is recommended and used by the Linux and Windows CI jobs. Install dependencies with `npm ci`. Set deployment environment variables externally or in `.env`/`.env.local`; externally supplied values take precedence, and `.env.local` overrides `.env` values.

`npm run build` generates the installed Prisma client, builds Next.js, and copies public/static assets into the standalone output using Node filesystem APIs. On Windows, client generation uses the installed matching engine through the existing Windows helper. `npm start` runs the standalone server with Node. Both commands leave database schema and data unchanged. Relative SQLite URLs resolve from the repository's `prisma` directory. Upload and export directories become absolute repository paths before the server starts from its standalone directory.

Run `npm run db:check` for read-only deployment preflight. A specific file can be checked with `node scripts/database-deploy.mjs --database /absolute/database.db --check`. The command accepts empty databases, complete legacy baseline databases, and known versioned states. It rejects partial schemas, unexpected tables/views/triggers, mismatched columns/types/nullability/keys, unique-index differences, foreign-key violations, corrupted databases, unknown migration receipts, and checksum drift.

`npm run db:deploy` applies only the versioned SQL files in `prisma/migrations`; `--database /absolute/database.db` selects a specific file. Deployment uses Node's SQLite runtime and records checksummed, completed receipts in Prisma's standard `_prisma_migrations` format. This command owns SQL execution and receipt creation; it does not invoke schema push or infer changes from the current schema. A complete existing baseline is adopted only after preflight. Before changing an existing database, it creates a consistent `VACUUM INTO` backup beside the file and prints the backup path.

The deployer acquires a bounded SQLite writer lock, repeats preflight under that lock, and retries backup preparation when another connection committed between backup and lock. SQL and migration receipts commit in one transaction; SQL or verification failures roll back all changes. Repeat deployment of an up-to-date database leaves it unchanged. Preserve the printed backup until the release is verified. Restore through an explicit operational recovery procedure, with application and worker processes stopped.

`npm run release:verify` runs types, tests with at most two workers, the production build, real HTTP workflow smoke tests, and platform smoke tests sequentially. Any failure exits nonzero. `npm run deploy:prepare` completes that verification before invoking database deployment; it does not publish the application or start a persistent server. The CI matrix uses these same portable commands on Linux and Windows. Start the application with `npm start` and the durable background worker separately with `npm run worker` after preparation succeeds.

Future schema changes require a new reviewed SQL migration in a timestamped directory. The deployer discovers migration directories in order, replays all applied SQL for preflight, and rejects gaps, duplicate receipts, and unknown migration names. Never edit a migration whose receipt has already been applied.

The release gate also requires an installed Chrome or Edge browser. Set `CHROME_PATH` when its executable is outside the standard Windows/Linux locations. The headless browser uses its own temporary profile and checks mobile keyboard navigation, history, refreshable detail links, reactive translation, real search, dialog labels/focus and tenant switching against the disposable production server. It does not use your browser profile or real account sessions.

Keep the worker running to capture genuine daily UTC analytics. The worker schedules tenant pages at startup and hourly; one idempotent snapshot per tenant/day records the first actual observation. Seeded historical charts are excluded, delayed jobs do not fabricate past observations, and provider costs remain unknown until actual cost provenance is available.
